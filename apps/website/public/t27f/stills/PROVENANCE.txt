/t27f/stills/ -- where every byte of a still comes from
=======================================================

A still is a T27F picture for a blog post (surface SF_STILL of t27 specs/t27f/frontend.t27). Its
pixels are drawn by a native t27b binary built from a .t27 spec; no hand-written script draws,
scales or colours any of them.

the-course-names-its-bench-board.png  (642 x 210, 5227 bytes)
  Post:      t27 specs/blog/course_bench_board.t27 (the figure block points here, STILL_HREF)
  Picture:   t27 specs/blog/course_bench_board_still.t27 (base 214 x 70, scale 3, four lines and
             one rule; board numbers from specs/boards/ax7203.t27)
  Program:   t27 specs/blog/course_bench_board_still_main.t27, built with
             `t27b build <spec> -o still.o --macho` and linked with ld; it writes one P6 file,
             404475 bytes, to standard output
  PNG:       the P6 re-encoded by sips; decoding the PNG back gives the same P6 bytes (cmp)
  Checked:   t27 specs/t27f/still_text_main.t27 reads the P6 and prints it as text, one
             character per 3 x 3 cell; mixed_cells 0, and the four lines and the rule read right

Not claimed: that a browser shows the PNG exactly as the text view reads the P6. The PNG was
checked by decoding it, not by looking at it in a browser.
